# Upgrade Pi to 1.6.1 and drop the local GPT-6.2 workaround

## Why

A gateway rename exposed a hole in the 1.3.0 catalog. `gpt-6.1-sol` /
`gpt-6-astra` were renamed to `gpt-6.2-sol` / `gpt-6.2-astra`, and because the
product model key *is* the upstream model string, the daemon no longer
recognised them: they missed `getBuiltinModel()` and were self-registered as
`openai-completions`. That silently changed the wire contract — no session
affinity headers, no `prompt_cache_key`, and a 200K/64K cap instead of
272K/128K — which showed up in production as prompt-cache hit rates of 99.2%
for `gpt-6-luna` against 36.7% for `gpt-6.2-sol` on the same gateway.

The previous patch taught `runner-pi` to keep renamed ids on the Responses API.
Pi 1.6.0 makes that knowledge upstream: `gpt-6.2-sol` and `gpt-6.2-astra` are
in the bundled catalog for the `openai`, `azure` and `openai-codex` providers
(272K context, 128K max output, reasoning, `off`/`minimal` unavailable).

`DYNAMIC_MODEL_PROFILES` is intentionally left alone. It is now a fallback
rather than the primary answer: a caller that reaches the gateway through a
custom provider id still misses the catalog lookup and still depends on the
declared `api: "openai-responses"` profile instead of silently landing on Chat
Completions.

Pi 1.6.1 also carries fixes that matter for exactly the traffic that made this
visible:

- More gateway failures are retried: Cloudflare HTTP 525, "provider is
  temporarily unavailable", partial-response errors, streams ending with
  `finish_reason: "error"`, and "request rate increased too quickly".
- GPT-6.2 no longer drops earlier reasoning as `prefix_mismatch` after the Codex
  WebSocket connection expires — dropped reasoning is a cache miss and a
  prefix mismatch on the next turn.
- OpenAI-compatible providers other than OpenAI now receive system messages
  (the system prompt and mid-conversation system messages) with the `system`
  role instead of a rewritten role.
- An unrelated error whose code merely contains `request_too_large`, such as
  `plugin_request_too_large`, no longer triggers compact-and-retry as if the
  context had overflowed.
- Sessions with very many entries after the last compaction (~120k+) no longer
  fail to load with `RangeError: Maximum call stack size exceeded`.

## Changes

- `@earendil-works/pi-{ai,agent-core,coding-agent,tui}` 1.3.0 → 1.6.1 in
  runner-pi, runner-cli, daemon and bunny-agent-tui. `pi-mcp-adapter` stays at
  5.3.1; its peer range accepts 1.6.1 and the MCP integration test passes
  against it.
- Both patches rebased onto 1.6.1:
  - pi-ai — unchanged behaviour: the thought-signature strip in
    `dist/api/transform-messages.js` and the `/context ?window ?exceeded/i`
    overflow pattern in `dist/utils/overflow.js` apply as-is.
  - pi-coding-agent — `dist/core/agent-session.js` applies with offsets; the
    `dist/core/system-prompt.js` hunk did not, because 1.6.x reworded the
    default opener ("operating inside pi" → "running inside pi"). Re-applied by
    hand so `appendAsPreamble` / `promptSections.preamble` still replace the
    default opener instead of appending after it.
- runner-pi: `DYNAMIC_MODEL_PROFILES`, the GPT-6 thinking-level map, the
  Responses compat block and the per-spec `api` / `compat` fields are unchanged.
  The catalog now answers the `openai` / `azure` / `openai-codex` lookups, so
  the profile only runs for a custom provider id; the comment above the GPT-6
  entries says so. `resolveDynamicModelRegistration()` keeps its job: unknown
  models still register on Chat Completions with
  `sendSessionAffinityHeaders: true`, and `PI_DYNAMIC_MODEL_API` still
  overrides the endpoint without a release.
- runner-pi: `packages/runner-pi/src/pi-ai-providers.d.ts` deleted — 1.6.1 ships
  types for `@earendil-works/pi-ai/providers/all`.
- runner-pi: `getBuiltinModel()` is now typed against a `BuiltinProvider` union,
  so the lookup for a caller-supplied provider goes through a narrow cast
  instead of a compile error. The runtime implementation is
  `MODELS[provider]?.[modelId]`, which returns `undefined` for unknown ids.
- daemon: `image-resize-packaging.test.ts` no longer insists on PNG. 1.6.x
  keeps whichever of PNG and JPEG is smaller at the configured quality, so a
  small opaque image now legitimately comes back as JPEG; the test accepts
  either and still checks the magic bytes, the 32×32 dimensions and the byte
  budget.
- New regression test in runner-pi that asserts the built-in catalog resolves
  `gpt-6.2-sol` and `gpt-6.2-astra` as Responses models with the 272K/128K
  profile — the exact lookup whose failure caused the downgrade.
- Docs: `docs/runner-maturity.md` version table and the installed-Pi note in
  `docs/search-citation-contract.md` now say 1.6.1.

## Verification

- Patches still carry their weight: reverting both patches in place makes 6
  tests red across `pi-ai-thought-signature-patch`, `pi-post-run-compaction-patch`
  and `pi-system-prompt-patch`; restoring them makes all 8 green.
- Full workspace: `pnpm -r build` and `pnpm -r typecheck` clean, `pnpm -r test`
  green — runner-pi 437, daemon 134, sdk 141, server-ai-sdk 95, server-acp 47,
  runner-cli 36, runner-harness 41, manager 221, runner-claude 75,
  sandbox-* 188, web 26, and the remaining runners (1–7 each).
- Request shape against a local OpenAI-compatible fake, through the built
  `runner-pi` dist:

  | model | endpoint | session header | `prompt_cache_key` | output cap |
  |---|---|---|---|---|
  | `openai:gpt-6.2-sol` | `/v1/responses` | `session-id` + `x-client-request-id` | yes | 128000 |
  | `openai:gpt-6.2-astra` | `/v1/responses` | `session-id` + `x-client-request-id` | yes | 128000 |
  | `openai:totally-unknown-model` | `/v1/chat/completions` | `session_id` + `x-session-affinity` | no (api.openai.com only) | — |
  | unknown + `PI_DYNAMIC_MODEL_API=openai-responses` | `/v1/responses` | `session-id` + `x-client-request-id` | yes | 64000 |

  Before this upgrade the first two rows went to `/v1/chat/completions` and the
  third row carried no session headers at all. The first two rows come from the
  built-in catalog; `gpt-6.2-sol` on a custom provider id still routes through
  `DYNAMIC_MODEL_PROFILES` and produces the same request.

Not verified: a run against a real gateway — no `llm.bika.ltd` key was available
here, so the 36.7% → 99% cache improvement is inferred from the request shape,
not measured. The Docker image build and the published `pi-mcp-adapter` 7.x
upgrade were not touched.
